• A variable named *token*, *nonce* or *csrf* assigned from rand(), mt_rand() or uniqid(): predictable. Use bin2hex(random_bytes(n)) sized to the storage column, or the core token API.
  • md5() / sha1() of a *pass* / *secret* variable: not a password hash. Use password_hash() / password_verify(). Compared with a value or passed as a Criteria value, it looks up a hash an old XOOPS stored (the 2.2 login fallback): a weak note to keep it only as a migration path and rehash on success once the password column holds modern hashes (the upgrader widens it to 255 in 2.5.8; before that a bcrypt hash would not fit).
  • ==, !=, strcmp() on a token, secret or password: '0e123' == '0e456' is true, and the comparison is not constant-time. Use hash_equals() on two strings. A comparison with a literal that is not a numeric string ($pass == '', $addtoken != false) is an emptiness or flag test and is not reported.

Fix: when both sides are request text (Request::getString() / getText() / getPath() / getUrl(), or Request::getVar() with a literal default and type 'string'), assigned nowhere else in the scope, != becomes !== and == becomes ===. For such values the strict form only ever rejects more, and only where the loose one calls two different inputs equal — the password-confirmation case of edituser.php. Everything else is report only: the token's storage width and consumers are unknown, so no generator is swapped in.
