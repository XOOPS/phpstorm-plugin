Raw $_GET / $_POST / $_COOKIE reads go through Xmf\Request; $_REQUEST is banned outright.

The rewrite is offered only where it preserves meaning: a keyed read becomes Request::getString('key', '', 'POST'), a keyed isset() becomes Request::hasVar(). A write, unset(), empty(), a === null comparison, a dynamic key or a bare $_POST are reported without a fix. An assignment to $_POST itself gets its own message: it changes what every later reader sees, Xmf\Request included, which may be the point.

Not inspected: Protector (the request firewall rewrites the raw superglobals before XOOPS boots), the core installer and upgrader (they run before the xoops_lib path is known, so Xmf\Request cannot load) and, like every security rule, test trees (tests/, test/, testdata/, fixtures/).
